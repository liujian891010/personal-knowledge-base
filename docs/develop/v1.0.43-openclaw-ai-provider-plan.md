# V1.0.43 OpenClaw AI Provider Plan

Status: Draft
Date: 2026-05-20

## Background

NoteApp currently keeps AI question answering local-first:

```text
AiWikiView
  -> local bridge /api/ai/ask
  -> desktop CLI ask-ai-wiki
  -> clients/desktop/service.py
  -> configured AI provider
```

The retrieval and citation layer is local. The model provider is only used after local AI Wiki pages have been matched and citations have been selected.

Current provider APIs:

```text
openai-completions
anthropic-messages
google-generative-ai
```

The provider dispatch lives in:

```text
clients/desktop/service.py
```

Relevant methods:

```text
DesktopService.answer_ai_wiki
DesktopService._answer_ai_wiki_with_provider
DesktopService._answer_ai_wiki_with_openai_provider
DesktopService._answer_ai_wiki_with_anthropic_provider
DesktopService._answer_ai_wiki_with_google_provider
```

## Goal

Allow NoteApp AI answering to use OpenClaw while preserving:

1. Local AI Wiki retrieval.
2. Existing citation prompt shape.
3. Existing frontend Ask AI Wiki UI.
4. Existing bridge and CLI boundary.
5. Existing fallback to deterministic local answers when no provider is configured.

## Recommendation

Use OpenClaw Gateway through its OpenAI-compatible Chat Completions endpoint first.

This should require no NoteApp code change if OpenClaw Gateway exposes:

```text
POST /v1/chat/completions
```

NoteApp already sends OpenAI-compatible chat-completions requests when `provider_api` is `openai-completions`.

## Zero-Code Configuration Path

Configure NoteApp AI settings as:

```text
provider_api: openai-completions
base_url: http://127.0.0.1:18789/v1
model_id: openclaw/default
api_key: <OpenClaw Gateway token/password>
```

With this configuration, NoteApp will call:

```text
http://127.0.0.1:18789/v1/chat/completions
```

The request body generated by NoteApp is already OpenAI-compatible:

```json
{
  "model": "openclaw/default",
  "temperature": 0.2,
  "messages": [
    {
      "role": "system",
      "content": "You answer questions for a local-first personal knowledge base. Use only the provided citations. If the citations are insufficient, say so. Cite sources inline as [1], [2]."
    },
    {
      "role": "user",
      "content": "Question:\n...\n\nCitations:\n..."
    }
  ]
}
```

Expected response shape:

```json
{
  "choices": [
    {
      "message": {
        "content": "..."
      }
    }
  ]
}
```

## OpenClaw Notes

OpenClaw should be treated as an agent gateway, not only as a raw LLM endpoint.

Important implications:

1. The `model_id` can represent an OpenClaw target such as `openclaw/default` or `openclaw/<agentId>`.
2. The actual downstream model should usually be configured in OpenClaw, not inside NoteApp.
3. If OpenClaw requires gateway-level token/password authentication, that credential is more sensitive than a normal model API key.
4. The OpenAI-compatible Gateway endpoint should remain loopback-only or otherwise protected by a trusted network boundary.

## Security Boundary

Current NoteApp local AI settings can store `api_key` in:

```text
.noteapp/settings.json
```

This may be acceptable for ordinary development keys, but it is not ideal for an OpenClaw operator-level gateway token.

Recommended follow-up before production:

1. Move AI provider secrets to system secure storage.
2. Keep `.noteapp/settings.json` for non-secret provider metadata only.
3. Avoid syncing OpenClaw gateway credentials through NoteApp sync.
4. Add UI copy that explains OpenClaw is a local or private gateway and that selected citations are sent to it.

## Validation Checklist

1. Start OpenClaw Gateway locally.
2. Enable its OpenAI-compatible Chat Completions endpoint.
3. Confirm a manual request works:

```powershell
curl.exe -s http://127.0.0.1:18789/v1/chat/completions `
  -H "Content-Type: application/json" `
  -H "Authorization: Bearer <token>" `
  -d "{\"model\":\"openclaw/default\",\"messages\":[{\"role\":\"user\",\"content\":\"Reply OK\"}]}"
```

4. In NoteApp Settings > AI, set:

```text
provider_api = openai-completions
base_url = http://127.0.0.1:18789/v1
model_id = openclaw/default
api_key = <token>
```

5. Click provider health check.
6. Compile AI Wiki if needed.
7. Ask a question in Ask AI Wiki.
8. Verify `model_status` starts with:

```text
openai-completions:openclaw/default
```

## When Code Changes Are Needed

Code changes are only needed if NoteApp should use OpenClaw-specific features beyond OpenAI-compatible chat completions.

Examples:

1. Use OpenClaw-native `/v1/responses`.
2. Send `x-openclaw-model`.
3. Send a stable `x-openclaw-session-key`.
4. Use OpenClaw-native agent sessions.
5. Use OpenClaw tool events or streaming events.
6. Display OpenClaw-specific gateway diagnostics in the Settings UI.

## First-Class Provider Design

If NoteApp needs first-class OpenClaw support, add a new provider API:

```text
openclaw-chat-completions
```

Required changes:

```text
clients/desktop/service.py
  Add openclaw-chat-completions to _LOCAL_SETTINGS_AI_PROVIDER_APIS.
  Add dispatch branch in _answer_ai_wiki_with_provider.
  Add _answer_ai_wiki_with_openclaw_provider.

apps/frontend/noteapp-web/src/runtimeConfig.ts
  Add OpenClaw preset.

apps/frontend/noteapp-web/scripts/sync-shell-bridge.mjs
  Add OpenClaw preset to bridge runtime model options.

apps/frontend/noteapp-web/src/views/SettingsView.tsx
  No structural change required if provider presets remain generic.

clients/desktop/tests/test_service.py
  Add provider dispatch and request-shape tests.

clients/desktop/tests/test_cli.py
  Add settings and health-path coverage if needed.
```

Suggested config fields:

```json
{
  "provider_api": "openclaw-chat-completions",
  "base_url": "http://127.0.0.1:18789/v1",
  "model_id": "openclaw/default",
  "api_key": "<token>",
  "openclaw_session_key": "noteapp-ai-wiki",
  "openclaw_downstream_model": null
}
```

For compatibility, the first-class provider can still call:

```text
POST /v1/chat/completions
```

but it may add OpenClaw-specific headers when configured:

```text
x-openclaw-session-key: noteapp-ai-wiki
x-openclaw-model: <downstream-model-id>
```

## Implementation Sketch

Provider dispatch:

```python
def _answer_ai_wiki_with_provider(...):
    if config.provider_api == "openclaw-chat-completions":
        return self._answer_ai_wiki_with_openclaw_provider(...)
    if config.provider_api == "anthropic-messages":
        return self._answer_ai_wiki_with_anthropic_provider(...)
    if config.provider_api == "google-generative-ai":
        return self._answer_ai_wiki_with_google_provider(...)
    return self._answer_ai_wiki_with_openai_provider(...)
```

Initial OpenClaw implementation can share most of the OpenAI-compatible request shape:

```python
request = Request(
    f"{config.base_url.rstrip('/')}/chat/completions",
    data=json.dumps(payload, ensure_ascii=False, separators=(",", ":")).encode("utf-8"),
    headers={
        "Accept": "application/json",
        "Authorization": f"Bearer {config.api_key}",
        "Content-Type": "application/json",
        "User-Agent": "pkb-desktop-ai/0.1",
        "x-openclaw-session-key": "noteapp-ai-wiki",
    },
    method="POST",
)
```

## Testing Strategy

Unit tests:

1. OpenClaw provider is accepted in local settings validation.
2. Provider dispatch selects `_answer_ai_wiki_with_openclaw_provider`.
3. Request URL is `<base_url>/chat/completions`.
4. Request body includes model, system prompt, user prompt and citations.
5. Response parser reads `choices[0].message.content`.
6. Non-2xx responses surface a useful error.
7. Empty answer fails cleanly.

Manual tests:

1. Gateway health check succeeds.
2. Ask AI Wiki returns an answer with inline citations.
3. Missing citations still returns the local no-citation status without calling OpenClaw.
4. Wrong token shows provider health error.

## Rollout Plan

### Phase 1: Configuration-Only Trial

1. Enable OpenClaw OpenAI-compatible endpoint.
2. Configure NoteApp as `openai-completions`.
3. Validate health check and Ask AI Wiki.
4. Collect prompt quality and latency observations.

### Phase 2: Preset Only

1. Add OpenClaw model preset to frontend runtime config.
2. Keep provider API as `openai-completions`.
3. No backend behavior change.

### Phase 3: First-Class Provider

1. Add `openclaw-chat-completions`.
2. Add optional OpenClaw headers.
3. Add tests and UI diagnostics.
4. Move secrets out of `.noteapp/settings.json` before production use.

## Recommendation

Start with Phase 1. It validates OpenClaw with the least risk because NoteApp already supports the OpenAI-compatible request and response format.

Only implement first-class OpenClaw support after there is a confirmed need for OpenClaw-native headers, sessions, responses API, streaming events, or richer diagnostics.
