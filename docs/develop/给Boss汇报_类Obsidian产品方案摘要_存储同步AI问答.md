# 类 Obsidian 产品方案汇报摘要

基于文档《类Obsidian软件最终可落地方案（本地优先+多端同步+AI知识库版）_v1.0.43》整理

## 一、汇报结论

这件事可以立项，但前提不是“先做一个像 Obsidian 的编辑器”，而是先把三件底层能力做对：

1. **存储模型要坚持本地优先**
2. **多端同步要稳定且可恢复，不能丢数据**
3. **AI 不能只是聊天入口，而要把知识持续沉淀成资产**

建议的 V1 目标不是“大而全”，而是做出一个真正可上线的闭环：

1. 桌面端本地知识库
2. 桌面端与桌面端同步
3. AI 知识编译与引用式问答

一句话概括：

**我们要做的不是“加了聊天框的笔记工具”，而是“本地优先、同步可靠、AI 可持续沉淀知识”的个人知识操作系统雏形。**

## 二、为什么值得做

市场上大量笔记产品只能解决“记录”和“查找”，但没有同时解决三个问题：

1. 用户是否真正拥有自己的原始数据
2. 多设备之间能否长期稳定同步
3. AI 产出能否沉淀为可复用知识，而不是一次性对话

本方案的差异化在于：

1. 用户主数据是本地文件，迁移和备份成本低
2. 同步层只是中转和收敛，不劫持用户主数据
3. AI 会持续生成 `.ai/wiki/` 知识页，后续问答、总结、写作都复用这一层

## 三、重点一：如何存储

### 3.1 存储总原则

整个产品采用三层边界：

1. **文件系统 = 主存储**
2. **SQLite = 本地索引、状态、缓存、AI 辅助层**
3. **云端 = 同步中转层和备份层**

这意味着：

1. 用户的 Markdown 笔记、附件、知识页都真实存在于本地目录
2. SQLite 不是主库，损坏后可以重建索引和状态
3. 云端不掌握明文主数据，只负责同步和对象存储

### 3.2 本地会存什么

本地 Vault 建议分为四类内容：

| 层 | 主要内容 | 作用 |
|------|------|------|
| 用户内容层 | `Notes/`、`Attachments/` | 保存笔记正文和附件 |
| 元数据层 | `.noteapp/filemap.json`、`sync.json` | 保存文件身份、同步状态、设备状态 |
| AI 知识层 | `.ai/wiki/`、`.ai/index.md` | 保存 AI 编译后的结构化知识页和索引 |
| 辅助状态层 | SQLite | 保存搜索索引、链接关系、同步日志、AI 任务状态 |

其中最关键的是两个对象：

1. `filemap.json`
   - 它是本地文件身份的唯一权威来源
   - 负责维护 `file_id -> path / status` 映射
   - 一个文件即使改名、移动，也保持同一个 `file_id`
2. `tombstone-ledger.jsonl`
   - 它记录“删除历史”
   - 目的是避免文件在多端之间被误删后又被错误复活
   - 即使 SQLite 损坏，也能帮助恢复删除状态

### 3.3 为什么必须这样设计

这样做的好处很明确：

1. **用户可迁移**
   - 主数据是 Markdown 和附件，不被数据库格式锁死
2. **可审计**
   - AI 产出的知识页是文件，不是黑盒数据库记录
3. **可备份**
   - 用户可以直接备份整个 Vault
4. **可恢复**
   - SQLite 负责效率，文件系统负责最终真实数据
5. **适合 AI**
   - AI 编译出来的内容直接成为知识库资产，而不是只停留在会话里

### 3.4 对老板需要强调的判断

这个方案不是“数据库驱动的云笔记”，而是“文件驱动的本地知识库”。

这是产品定位，也是商业上的信任基础。因为一旦主数据不在本地，产品会很快退化成普通 SaaS 笔记工具，很难和市场上现有产品拉开差距。

## 四、重点二：如何多端同步

### 4.1 同步设计的核心目标

同步层只做三件事：

1. 保证多端一致
2. 保证不丢数据
3. 保证本地优先

换句话说，同步不是“把云端当主库往下覆盖”，而是“以本地文件为基础，通过协议把多个设备收敛到一致状态”。

### 4.2 我们采用的同步思路

V1 采用的是：

**全量 Manifest 快照 + 增量 Blob 上传 + CAS 并发控制**

可以用一句业务化的话理解：

1. 文件内容按变更增量上传，不重复传没变的内容
2. 每次提交时，上传的是“当前整个 Vault 的最新目录快照”
3. 服务端用版本号和 CAS 保证不会把别人刚提交的数据覆盖掉

关键对象包括：

1. `revision`
   - 每次成功提交后，云端版本号递增
2. `base_revision`
   - 本次提交是基于哪个版本做的
3. `manifest`
   - 当前整库文件清单快照
4. `tombstone`
   - 删除记录，不靠“文件不见了”来推断删除
5. `acked_revision`
   - 每台设备确认自己已经安全应用到哪个版本

### 4.3 一次同步是怎么工作的

提交路径：

1. 设备先扫描本地变化
2. 只上传新增或变化的 blob
3. 再提交当前整库 manifest
4. 服务端检查 `base_revision` 是否仍然是最新
5. 如果是，则生成新 `revision`
6. 客户端本地更新同步状态，并把本次删除记录正式落账

拉取路径：

1. 设备先问服务端当前最新 `head revision`
2. 如果远端更新了，就拉取最新 manifest
3. 对比本地工作区和远端状态
4. clean 文件直接收敛
5. dirty 文件优先保护本地修改，必要时做 merge 或生成冲突副本
6. 全部完成后，再重写本地 `filemap.json`

### 4.4 为什么不用“网盘式同步”

因为网盘式同步最大的问题是：

1. 它通常只认路径，不认文件身份
2. 删除、改名、移动、冲突很容易出问题
3. 对 dirty working tree 保护不足
4. 一旦崩溃或中途中断，恢复过程不可解释

本方案的同步层引入 `file_id`、`manifest`、`tombstone`、`journal`，就是为了解决这些“看起来不性感，但决定产品口碑”的问题。

### 4.5 如何保证不丢数据

这部分是 V1 最重要的技术壁垒：

1. **CAS 并发控制**
   - 两台设备同时提交时，后提交者不会直接覆盖前者
2. **dirty working tree 保护**
   - 本地有未提交修改时，远端更新不能直接把本地文件盖掉
3. **冲突副本机制**
   - 冲突时先保住两边内容，再让用户选择
4. **两阶段落盘**
   - 处理改名、路径交换、批量占位时先写 staging，再写最终路径
5. **崩溃恢复 journal**
   - 同步中断后可以按步骤继续恢复，不会出现“半成功半失败”的黑盒状态
6. **tombstone 回收机制**
   - 删除不会立即消失，必须等所有相关设备都确认收到删除后，才允许清理

### 4.6 对老板需要强调的判断

同步不是“后端顺手做一下”的功能，而是这个产品最核心的可信度来源。

如果同步不稳，用户对产品的第一反应不会是“AI 很强”，而是“这东西会不会把我资料搞丢”。所以原方案才明确要求：**同步协议必须先于业务开发冻结。**

### 4.7 V1 同步边界

为了保证交付，V1 明确只做：

1. 桌面端与桌面端同步
2. 端到端加密
3. 冲突副本
4. 断点续传
5. 设备管理和 tombstone 回收闭环

V1 明确不做：

1. Git / WebDAV 多协议同步
2. delta sync
3. 移动端后台强实时同步承诺

这样收缩的好处是：先把“可靠同步”做扎实，而不是一开始把协议复杂度做爆。

## 五、重点三：如何结合 AI 实现问答

### 5.1 AI 不是聊天框，而是知识编译器

这份方案最重要的 AI 判断是：

**不把 AI 作为“临时 RAG 助手”，而是把 AI 作为“知识编译器”。**

意思是：

1. AI 不只是临时从散乱笔记里捞几段上下文回答问题
2. AI 要持续把原始资料整理成结构化知识页
3. 之后的问答、总结、写作都优先基于知识页完成

### 5.2 AI 的三层结构

AI 侧采用三层结构：

| 层 | 内容 | 作用 |
|------|------|------|
| Raw Layer | 原始笔记、附件抽取文本、外部资料 | 保存原始素材 |
| Wiki Layer | 主题页、实体页、时间线页、QA 页、总结页 | 形成稳定知识资产 |
| Schema / Control Layer | `AGENTS.md`、命名规则、引用规则、lint 规则 | 保证知识页质量和一致性 |

这意味着 AI 产出不是一次性文本，而是一个可持续维护的知识层。

### 5.3 AI 的工作流

完整链路是四步：

1. **Ingest**
   - 输入可以是当前笔记、文件夹、搜索结果、外部资料，甚至整个 Vault
2. **Compile**
   - AI 按统一 schema 把原始内容编译成结构化 wiki 页面
3. **Index**
   - 更新 `.ai/index.md`、实体映射、页面链接
4. **Ask**
   - 用户提问时先查 wiki，不足时再回查 raw 和 note chunks

### 5.4 问答是怎么实现的

问答链路建议理解为：

1. 用户提问
2. 选择范围
3. 优先检索 `.ai/wiki/`
4. wiki 信息不足，再回查 raw、笔记 chunk、附件抽取结果
5. 组装上下文
6. 模型生成回答
7. 返回引用来源

因此它和传统“整库直接问答”的区别是：

1. 回答更稳定
2. 引用更可追溯
3. 越用知识库越好，而不是每次都从原始碎片重新拼

### 5.5 为什么不是“纯 RAG”

纯 RAG 的问题是：

1. 每次问答都在原始碎片中临时捞上下文
2. 结果质量波动大
3. 不容易沉淀成长期知识资产

本方案采用“编译型知识库”的收益是：

1. 可以持续形成主题页、实体页、时间线页、QA 页
2. 问答和写作共享同一个知识中枢
3. 用户越用，知识层越完整，产品壁垒越深

### 5.6 AI 输出如何写回

AI 可以输出：

1. 问答
2. 总结
3. 大纲
4. 新知识页
5. 对既有知识页的更新建议

但有一个强约束：

**默认必须用户确认后才写回。**

明确禁止：

1. 后台静默改写
2. 全库自动覆盖

同时，对于已经有人手工修改过的知识页，系统会保留：

1. `user_edited` 标记
2. `locked` 标记
3. diff 确认机制

目的很简单：AI 生成可以快，但知识资产的最终控制权必须在用户手里。

### 5.7 隐私边界怎么处理

AI 与同步的边界是这个方案的另一个亮点：

1. 本地文件系统保存明文，便于编辑和 AI 读取
2. 同步到云端前，由客户端本地加密
3. 云端只接触加密 blob 和 manifest 元数据
4. AI 调用读取的是本地明文，不是云端密文
5. V1 推荐客户端 BYOK 直连模型 API，不经过自建服务端转发明文

这意味着：

1. 同步服务端不持有用户明文主数据
2. AI 调用链路足够清晰，隐私边界可解释
3. 前期平台不需要承担大额模型成本

## 六、实施建议

### 6.1 建议的上线策略

建议按四段推进：

1. 阶段 0：POC，验证 Rust Core、SQLite FTS、对象存储、最小 AI 链路
2. 阶段 1：先做桌面端本地可用
3. 阶段 2：做桌面端同步闭环和知识页问答 MVP
4. 阶段 3：稳定化后发布

移动端建议放到 V1.1，以最小接入方式补齐浏览、简单编辑、前台同步和简易 AI。

### 6.2 更现实的周期

按原方案估算：

1. **V1（桌面 + 桌面同步 + 桌面 AI MVP）：3-4.5 个月**
2. **V1.1（补移动端最小接入）：4.5-6 个月**

如果希望把 V1 压到 3-4 个月，必须进一步收缩：

1. iOS 延后
2. Linux 延后
3. AI 只保留当前笔记总结和知识页问答 MVP

### 6.3 成本判断

前期服务端成本并不高，1000 用户以内大致可控在较低区间。

原方案估算：

1. 初期月成本约 **100-540 元**
2. 1000 用户、平均 500MB 存储时，月成本约 **500-800 元**
3. AI 建议 V1 采用 **BYOK**，优先把模型成本转移给用户或高阶套餐

### 6.4 关键风险

最主要风险不是 UI，而是三类基础风险：

1. **同步复杂度高**
   - 一旦协议没定好，后期返工成本极大
2. **Rust Core / FFI 集成风险**
   - 会直接影响多端统一内核策略
3. **AI 范围失控**
   - 如果 V1 一开始追求“整库直接问答 + 全自动编译 + 全平台覆盖”，很容易把项目拖死

### 6.5 建议老板拍板的事项

建议本轮只做以下决策：

1. 是否按“桌面端优先”立项
2. 是否接受“文件系统为主存储、SQLite 为辅助层”的架构路线
3. 是否接受“Manifest + CAS + Tombstone”作为同步底座
4. 是否接受“AI 知识编译”而不是“纯聊天 RAG”作为产品主线
5. 是否接受移动端延后到 V1.1

## 七、最终建议

如果目标是做一个真正有竞争力、能建立用户信任的类 Obsidian 产品，那么最应该坚持的是：

1. **本地文件必须是主数据**
2. **同步必须可靠且可恢复**
3. **AI 必须把原始资料持续沉淀成知识页**

因此建议的执行结论是：

1. **立项通过**
2. **桌面端优先**
3. **先做同步底座，再做业务层扩展**
4. **AI 以 `.ai/wiki/` 为知识中枢**
5. **V1 做闭环，不做大而全**

这条路线的价值不在于“看起来像不像 Obsidian”，而在于能否同时建立三种能力：

1. 用户对数据主权的信任
2. 用户对同步稳定性的信任
3. 用户对 AI 产出可复用、可沉淀的认知

如果这三件事做成，这个产品就不只是笔记软件，而是具备长期复利能力的知识基础设施。
