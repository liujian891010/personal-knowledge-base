# v1.0.43 AI Writeback API Design

Updated: 2026-05-18

`V1043-M4-01` freezes the local AI writeback contract for `V1043-M4-02` and `V1043-M4-03`. AI writeback remains a desktop/local bridge capability. The sync server is not involved except when the user later syncs encrypted note changes through the normal E2EE commit path.

## Scope

This design extends the existing AI context task flow:

1. `preview`: already implemented by `DesktopSyncService.run_ai_context_task`.
2. `insert_current_note`: append a confirmed AI result into the current note draft.
3. `create_note`: save a confirmed AI result as a user-visible Markdown knowledge page.

The first implementation must not write directly to `.ai/wiki/`. AI Wiki pages remain compiler-owned system artifacts and keep their existing `locked` / `user_edited` overwrite protection.

## Bridge Endpoints

The desktop bridge exposes two local-only endpoints:

```text
POST /api/ai/writeback/preview
POST /api/ai/writeback/apply
```

Both endpoints accept JSON only and return the same contract shape as CLI/service methods. The bridge must reject requests when no active workspace is selected.

## Request Shape

```ts
type AiWritebackMode = 'insert_current_note' | 'create_note';

type AiWritebackSource = {
  file_id: string;
  path: string;
  title?: string;
  excerpt?: string;
};

type AiWritebackRequest = {
  schema_version: 'v1';
  idempotency_key: string;
  mode: AiWritebackMode;
  answer_markdown: string;
  instruction?: string;
  sources: AiWritebackSource[];
  target:
    | {
        type: 'current_note';
        file_id: string;
        insert_position: 'append';
      }
    | {
        type: 'new_note';
        target_path?: string;
        title?: string;
        folder_path?: 'AI Notes' | string;
      };
};
```

Rules:

1. `answer_markdown` must be non-empty Markdown.
2. `sources` may be empty only when `model_status` is `no_context_sources` or the user explicitly confirms source-free draft output.
3. `insert_position` is `append` for V1. Cursor insertion is deferred because it depends on editor state.
4. `target_path` must be normalized, workspace-relative, Markdown-only, and outside `.noteapp/`, `.ai/`, `Attachments/`, and trash.
5. `idempotency_key` is required so retrying an apply request does not duplicate content.

## Preview Response

`/preview` performs all validation and returns a confirmation token, but it must not change disk, draft, filemap, search index, or sync state.

```ts
type AiWritebackPreview = {
  schema_version: 'v1';
  mode: AiWritebackMode;
  target_path: string;
  before_hash: string | null;
  after_hash: string;
  confirmation_token: string;
  expires_at_ms: number;
  rendered_markdown: string;
  diff: {
    format: 'unified';
    text: string;
  };
  warnings: string[];
};
```

`confirmation_token` is a server-local HMAC or hash over `vault_id`, `mode`, target identity, `before_hash`, `after_hash`, `idempotency_key`, and expiry. `/apply` must recompute or verify it before writing.

## Apply Response

`/apply` requires the original request plus `confirmation_token`.

```ts
type AiWritebackApplyRequest = AiWritebackRequest & {
  confirmation_token: string;
};

type AiWritebackApplyResult = {
  schema_version: 'v1';
  mode: AiWritebackMode;
  status: 'applied' | 'already_applied';
  file_id: string;
  path: string;
  content_hash: string;
  wrote_draft: boolean;
  wrote_file: boolean;
  search_index_refreshed: boolean;
  requires_user_save: boolean;
};
```

## Insert Current Note

Preview uses the current editor draft as the base text when a draft exists; otherwise it uses disk content. The inserted block format is:

```md
## AI Generated - 2026-05-18 20:30

<answer_markdown>

### Sources

- [[Source Title]] (`Notes/source.md`)
```

Apply writes only the workspace draft for `file_id`. It must not write the Markdown file directly. The user still reviews and saves through the existing editor flow. Because only the draft changes, `search_index_refreshed` is `false` and `requires_user_save` is `true`. The existing save path later writes the file, clears the draft, refreshes the search index, and lets normal sync change detection pick up the edit.

If the base draft/file changed after preview, apply must fail with `ai_writeback_base_changed` and return a fresh preview instruction to the UI.

## Create Note

Default target:

```text
AI Notes/YYYY-MM-DD <safe-title>.md
```

Apply writes a new Markdown file atomically, adds or updates its filemap record, and refreshes the search index before returning success. It must never mutate `last_synced_revision`; the normal sync scanner owns that state.

Created notes include frontmatter:

```md
---
type: ai_generated_note
created_at: 2026-05-18T20:30:00+08:00
source_count: 2
user_edited: false
locked: false
---
```

If `target_path` already exists, the service must either choose a deterministic `-2`, `-3` suffix or reject with `ai_writeback_target_exists`; it must not silently overwrite.

## Protection Rules

1. Targets under `.ai/`, `.noteapp/`, `Attachments/`, or trash are rejected by default.
2. Existing Markdown with frontmatter `locked: true` is never modified by AI writeback.
3. Existing AI-generated Markdown with `user_edited: true` is never overwritten by `create_note`.
4. `insert_current_note` may append to a normal user note after explicit confirmation, but it must reject locked notes.
5. The AI Wiki compiler keeps its current behavior: pages marked `locked` or `user_edited` are skipped.

## Error Codes

| Code | Meaning |
| --- | --- |
| `ai_writeback_invalid_request` | Malformed request or unsupported mode |
| `ai_writeback_missing_confirmation` | Apply called without a valid preview token |
| `ai_writeback_base_changed` | Target content changed after preview |
| `ai_writeback_target_locked` | Target has `locked: true` |
| `ai_writeback_user_edited` | Existing generated target has `user_edited: true` |
| `ai_writeback_target_exists` | New note target exists and suffixing was not requested |
| `ai_writeback_index_refresh_failed` | File was written but search index refresh failed |

## Implementation Order

1. Add service dataclasses and `preview_ai_writeback` / `apply_ai_writeback`.
2. Add CLI commands `ai-writeback-preview` and `ai-writeback-apply`.
3. Add bridge endpoints using the same request/response schema.
4. Implement `insert_current_note` as draft-only append.
5. Implement `create_note` with filemap and search index refresh.
6. Add focused tests for base-change rejection, locked/user-edited protection, idempotent apply, and search index refresh.
