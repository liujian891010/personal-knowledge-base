# v1.0.43 Blob 断点续传协议设计

任务：`V1043-M2-05` / `V1043-M2-06`

## 结论

Blob 断点续传冻结为“加密后分片”协议：客户端先生成完整 encrypted blob，再按固定 `chunk_size` 切分密文字节流。服务端只接收密文分片、分片偏移和最终密文校验材料，不接触明文、不参与 E2EE。

当前文档冻结协议语义，并记录 `V1043-M2-06` 的上传续传落地状态。客户端下载重试/续传仍归入 `V1043-M2-07`。

## 上传流程

1. 客户端完成 `blob_id`、`encrypted_size`、`encrypted_sha256`、`content_hash` 计算。
2. 客户端按 `chunk_size` 生成 chunk 表，默认 `4 MiB`。
3. 客户端调用 `/vaults/{vaultId}/blobs/resumable-upload-init`。
4. 服务端返回 `session_id`、`upload_url`、已存在分片、缺失分片。
5. 客户端只上传 `missing_chunks`。
6. 客户端调用 `/vaults/{vaultId}/blobs/resumable-upload-complete`。
7. 服务端验证所有分片存在、拼接后的 `encrypted_size` 和 `encrypted_sha256` 一致后，才把 blob 标记为可提交引用。

## Chunk 规则

- `chunk_id = "chunk-" + sha256(blob_id + ":" + offset + ":" + size).hexdigest()[:32]`
- `offset` 是 encrypted blob 字节偏移，从 0 开始。
- `size` 是该分片密文字节数，最后一片可以小于 `chunk_size`。
- `encrypted_size=0` 时仍生成一个 `offset=0,size=0` 的空分片描述，避免空 blob 在状态机里没有完成边界。
- 客户端重试同一 `chunk_id` 必须幂等；服务端如果已持有相同 `chunk_id` 和相同大小，返回 uploaded，不要求重复上传。

## 下载流程

1. 客户端根据本地临时文件长度或缺失范围生成 `ranges`。
2. 客户端调用 `/vaults/{vaultId}/blobs/resumable-download-init`。
3. 服务端返回可下载的 range capability。
4. 客户端按 range 下载并写入临时文件对应偏移。
5. 客户端只有在本地累计字节等于 `encrypted_size` 后，才进入解密。
6. 解密后必须继续校验明文 `content_hash`，失败时不得写入工作区。

## 错误语义

| 场景 | 服务端/客户端行为 |
| --- | --- |
| 上传中断 | 再次 upload-init 返回已上传与缺失分片，客户端继续缺失分片 |
| complete 时缺分片 | 返回 `status=incomplete` 和 `missing_chunks`，不得提交不完整 blob |
| encrypted_sha256 不匹配 | 服务端拒绝 complete，客户端必须重新上传或放弃 session |
| 下载 range 不合法 | 服务端返回 400，客户端不得自行猜测修正 |
| 下载中断 | 客户端保留临时文件和已完成 ranges，下次重新请求缺失 ranges |
| 解密失败 | 视为错误密钥、损坏 blob 或服务端异常，不写入工作区 |
