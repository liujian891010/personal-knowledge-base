# 桌面客户端 + 中心同步服务开发方案

## 1. 目标

当前项目的实际运行形态是：

1. 前端页面运行在本机。
2. 本地 bridge 运行在本机。
3. 工作区文件直接读写本机文件系统。
4. 同步后端仍是本地开发 MVP。

这意味着它现在更像“开发态本地工具”，还不是“别人安装后即可稳定使用的产品”。

接下来统一按以下方向推进：

1. **客户端形态**：桌面客户端。
2. **协同形态**：中心同步服务。
3. **数据原则**：本地优先，云端只做同步与授权，不劫持主数据。
4. **AI 原则**：AI 能力保留在客户端侧编排，中心服务不承接知识编译主逻辑。

目标结果是：

1. 用户安装桌面客户端后，可直接选择本机工作区开始使用。
2. 多个用户或同一用户多台设备，可通过中心同步服务同步同一 vault。
3. 客户端不再要求用户手工分别启动 `vite`、`sync:bridge`、本地 Python 服务。

## 2. 不再采用的形态

当前不把“纯 Web 页面部署后直接给别人用”作为主路线，原因如下：

1. 现有文件树、草稿、搜索、回收站、AI 会话都依赖本地 bridge。
2. 工作区是用户本机文件夹，不是服务端文件空间。
3. 纯 Web 模式会把当前“本地优先”产品边界整体改掉，成本过高。

因此后续产品化的主路线是：

1. **桌面客户端承载本地能力**
2. **中心服务承载同步与账号能力**

## 3. 目标架构

### 3.1 总体结构

```text
用户电脑
  ├─ 桌面客户端外壳
  ├─ 本地 UI（前端）
  ├─ 本地应用服务层（现 bridge / desktop service 演进而来）
  ├─ 本地工作区文件系统
  ├─ 本地 SQLite / filemap / drafts / AI sessions
  └─ 本地 AI 调用配置

中心云端
  ├─ 账号与设备服务
  ├─ vault 同步服务
  ├─ 对象存储
  ├─ 元数据数据库
  └─ 监控 / 日志 / 运维系统
```

### 3.2 边界划分

**桌面客户端负责：**

1. 工作区选择与本地文件读写。
2. Markdown 编辑、搜索、双链、回收站、AI 文档。
3. 本地索引、草稿、AI 会话、AI Wiki 编译。
4. 调用同步服务完成 pull / commit / ack。
5. 管理用户本机的 AI Key 和本地偏好。

**中心同步服务负责：**

1. 登录鉴权。
2. 设备注册与撤销。
3. vault head / manifest / commit / ack。
4. blob 上传下载授权。
5. 设备活跃状态与 `acked_revision` 维护。
6. tombstone 回收资格判定。

**对象存储负责：**

1. 加密 blob 的持久化。
2. 上传下载能力链接的真实落点。

## 4. 客户端目标形态

## 4.1 运行方式

最终用户不再手工启动以下进程：

1. `npm run dev`
2. `npm run sync:bridge`
3. `uvicorn main:app`

应改为：

1. 安装桌面客户端。
2. 启动桌面客户端。
3. 客户端自动拉起本地应用服务层。
4. UI 自动连接本地服务层。

### 4.2 客户端内部组成

建议拆成三层：

1. **桌面壳层**
   - 负责窗口、菜单、自动更新、崩溃恢复、启动本地服务。
2. **本地应用服务层**
   - 负责桥接文件系统、桌面 service、AI 会话、工作区 registry、同步动作。
3. **前端 UI**
   - 负责界面渲染与交互，不直接依赖浏览器能力做关键业务。

### 4.3 客户端必须补齐的产品能力

1. 首次启动引导。
2. 登录态接入桌面客户端，而不是只放在浏览器 `sessionStorage`。
3. 工作区选择、切换、失效修复。
4. bridge / 本地服务健康检查与自动恢复。
5. 崩溃日志导出。
6. 安装包升级机制。
7. 设置页改成“产品设置”，而非“开发态配置面板”。

## 5. 中心同步服务目标形态

### 5.1 当前状态

当前 `apps/backend/noteapp-server` 仍是本地开发 MVP，不适合作为正式中心服务直接对外。

当前缺口包括：

1. 没有正式账号模型。
2. 没有持久数据库。
3. 没有真实对象存储。
4. token 生命周期管理不足。
5. 没有 tombstone 回收策略闭环。
6. 仍保留本地 bootstrap 的临时放宽逻辑。

### 5.2 正式中心服务必须具备

1. 用户账号体系。
2. 设备注册、设备撤销、设备心跳。
3. vault 成员关系。
4. `GET /vaults/:vaultId/devices` 等设备管理接口。
5. manifest / head / revisions / commit / ack 正式存储。
6. 真实 blob 上传下载授权。
7. tombstone 回收资格判定与后台清理任务。
8. 审计日志、监控告警、备份恢复。

### 5.3 存储层建议

建议正式中心服务至少包含：

1. **关系型数据库**
   - 用户、设备、vault、revision 元数据、成员关系、capability、审计日志。
2. **对象存储**
   - 加密 blob。
3. **缓存 / 队列（可后置）**
   - capability、异步回收、后台任务。

`V1043-M3-01` 已冻结生产后端架构方案，详见 [v1.0.43-production-backend-architecture.md](./v1.0.43-production-backend-architecture.md)。数据库路线为 M3 内测 / V1 初期优先托管 SQLite（Turso / Cloudflare D1 等），通过 repository 层隔离方言；V1 稳定期按写入延迟、事务语义、备份恢复和查询复杂度评估是否迁移 PostgreSQL。

### 5.4 生产后端架构冻结

M3 不重写同步主链路，也不把当前本地 JSON store 直接暴露为生产服务。正式中心服务按以下边界演进：

1. 保留现有 FastAPI 同步 API 的主链路语义，新增账号登录、refresh token、vault 创建 / 绑定等生产入口。
2. 所有 vault 级 API 在生产配置下必须要求 `Authorization`，本地 bootstrap 放宽只允许 dev/test profile 显式启用。
3. `revision`、`manifest`、`ack`、`file_versions`、`capability` 和 tombstone GC 审计全部进入关系型数据库。
4. 加密 blob 进入 S3/OSS 兼容对象存储，客户端仍只能通过 `upload-init` / `download-init` 获取受控能力。
5. commit CAS 以数据库事务串行化同一 `vault_id` 的 head 推进，不能继续依赖单进程锁。
6. 设备撤销必须同时吊销 access token、refresh token、session 和未使用 capability。

## 6. 推荐演进路径

## 阶段 A：内测桌面版

目标：

1. 先把“开发态三进程”收敛为“一个桌面安装包”。
2. 中心服务仍可先用受控测试环境。

交付：

1. Windows 桌面安装包。
2. 自动启动本地服务层。
3. 用户可登录、选工作区、编辑、搜索、AI 文档、同步。

暂不强求：

1. 自动更新全量打通。
2. 移动端接入。
3. SaaS 化租户体系。

## 阶段 B：中心同步服务生产化

目标：

1. 让多用户、多设备可长期稳定使用。
2. 摆脱本地开发态 Python JSON store。

交付：

1. 正式数据库与对象存储。
2. 账号、设备、vault、鉴权闭环。
3. 运维与监控能力。

## 阶段 C：规模化交付

目标：

1. 支持团队内正式推广。
2. 支持安装、升级、回滚、问题排查。

交付：

1. 客户端自动更新。
2. 服务端多环境部署。
3. 灰度与回滚机制。

## 7. 客户端开发拆解

### 7.1 桌面壳层

需要完成：

1. 选型并固定桌面壳。
2. 应用启动时自动拉起本地服务层。
3. 应用退出时安全回收本地子进程。
4. 提供原生文件夹选择器。
5. 提供原生通知、日志目录、诊断入口。

验收口径：

1. 用户双击应用即可启动。
2. 无需手工开 terminal。
3. 本地服务异常时能在 UI 给出明确提示。

### 7.2 本地服务层

建议把现在这些能力统一收口：

1. `sync-shell-bridge.mjs`
2. workspace files / content / draft / trash / search / links API
3. AI chat sessions API
4. AI provider health API
5. desktop service 调用入口

需要完成：

1. 统一成本地桌面服务进程。
2. 统一错误码与日志格式。
3. 统一工作区 registry 与活动工作区刷新机制。
4. 去掉开发态 fixture fallback 依赖。

### 7.3 UI 层

需要完成：

1. 去开发态入口与隐藏逻辑分叉。
2. 明确正式开放菜单。
3. 增加桌面场景的状态提示：
   - 本地服务未启动
   - 同步服务不可达
   - 工作区路径失效
   - 需要重新登录
4. 增加设备管理页。
5. 增加同步状态页正式入口。

## 8. 中心服务开发拆解

### 8.1 账号与鉴权

需要完成：

1. 用户登录。
2. access token / refresh token。
3. 设备与账号绑定。
4. 设备撤销后 token 立即失效。

### 8.2 vault 同步核心

需要完成：

1. head / manifest / revisions / commit / resolve-intent / ack。
2. vault 成员关系维护。
3. `acked_revision` 更新规则。
4. CAS 并发控制。

### 8.3 blob 服务

需要完成：

1. upload-init。
2. download-init。
3. capability 生命周期与撤销。
4. 对接真实对象存储。

### 8.4 设备管理与 tombstone 回收

需要完成：

1. `GET /vaults/:vaultId/devices`
2. `POST /devices/:deviceId/heartbeat`
3. `DELETE /devices/:deviceId`
4. tombstone GC worker
5. 回收资格判定与最短保留期策略

## 9. 关键产品流程

### 9.1 首次使用

1. 安装桌面客户端。
2. 登录账号。
3. 创建或选择本地工作区。
4. 绑定或创建 vault。
5. 进入笔记库。

### 9.2 已有用户新设备接入

1. 安装桌面客户端。
2. 登录账号。
3. 注册设备。
4. 选择本地工作区目录。
5. 通过中心服务完成首轮 pull。
6. 建立本地索引与 AI 会话目录。

### 9.3 日常同步

1. 本地编辑。
2. 本地落盘。
3. 本地检测变更。
4. commit 到中心服务。
5. 其他设备 pull 并 apply。

## 10. 部署方案

### 10.1 内测环境

适合 5-20 人试用。

建议：

1. 客户端提供 Windows 安装包。
2. 中心服务部署一套测试环境。
3. 对象存储可先用云厂商现成 bucket。
4. AI Key 仍采用 BYOK。

### 10.2 正式生产环境

至少拆分：

1. 网关层
2. 账号服务 / 同步服务
3. 数据库
4. 对象存储
5. 日志与监控

建议具备：

1. 灰度环境
2. 备份恢复
3. 服务健康探针
4. 错误告警

## 11. 阶段优先级

### P0

1. 固定产品形态为桌面客户端 + 中心同步服务。
2. 不再继续强化“浏览器开发态直接交付”的路径。
3. 冻结客户端与中心服务边界。

### P1

1. 桌面壳层打包。
2. 本地服务层收口。
3. 工作区切换、登录、同步状态正式入口。

### P2

1. 中心服务生产化。
2. 账号、设备、对象存储、正式 DB。
3. 设备管理和 tombstone 回收闭环。

### P3

1. 自动更新。
2. 安装包签名。
3. 监控、审计、诊断。

## 12. 第一版交付标准

满足以下条件，才算进入“可给别人用”的第一版：

1. 用户安装桌面客户端后，无需手工启动开发命令。
2. 用户可以登录并退出登录。
3. 用户可以选择本机工作区。
4. 用户可以进行 Markdown 编辑、搜索、双链、回收站、AI 文档。
5. 用户可以连接中心同步服务完成多设备同步。
6. 服务端具备正式账号、设备、vault、blob、数据库和基础监控能力。

## 13. 当前明确不在本轮范围

1. 纯 Web SaaS 版。
2. 移动端正式接入。
3. 多人实时协作。
4. 插件市场。
5. 平台级 AI 统一计费。

## 15. 结论

后续产品化路线明确为：

1. **本地开发态工具**
   ->
2. **桌面客户端内测版**
   ->
3. **桌面客户端 + 中心同步服务正式版**

短期最关键的不是继续堆浏览器页面，而是：

1. 收口桌面客户端形态。
2. 收口本地服务层。
3. 生产化中心同步服务。

只有这样，这个项目才真正具备“供其他人使用”的交付基础。
