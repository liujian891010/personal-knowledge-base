# V1.0.43 Cloud KB Connector Plan

Status: Draft
Date: 2026-05-20

## 背景

NoteApp 当前采用 local-first 架构：本地 workspace 是主工作区，Web 前端通过本机 bridge 读写 Markdown、附件、搜索索引、AI Wiki 和图谱数据；云端同步后端只负责在设备之间传递加密后的 workspace 变更。

如果需要对接现有云端知识库，推荐采用“Cloud KB Connector 同步成本地 workspace”的方案，而不是让前端直接访问云端知识库，也不是立即重写现有 sync server 协议。

目标路径：

```text
Cloud KB API
  -> Cloud KB Connector
  -> local workspace Markdown / Attachments / .noteapp mapping state
  -> existing search / graph / AI Wiki / editor / sync / E2EE flow
```

## 目标

1. 将现有云端知识库作为外部数据源接入 NoteApp。
2. 将云端文档 materialize 为本地 workspace 中的 Markdown 和附件。
3. 复用现有本地搜索、图谱、AI Wiki、编辑器、版本和 E2EE 同步能力。
4. 将云端鉴权、增量同步、冲突检测放在 desktop bridge / desktop core 层。
5. 首版优先支持只读导入和手动同步，后续再支持增量同步、冲突 UI 和双向写回。

## 非目标

1. 首版不要求现有云端知识库实现 NoteApp sync API。
2. 首版不做双向写回云端。
3. 首版不在前端保存或暴露云端 access token、refresh token 或 client secret。
4. 首版不自动合并本地与云端冲突内容。

## 核心原则

1. 本地 workspace 仍是主工作区，云端知识库只是一个 source。
2. 前端只调用本机 bridge，不直接调用云端知识库 API。
3. 云端文档统一转换为 workspace-relative Markdown。
4. 附件统一落到 `Attachments/` 下。
5. `.noteapp/` 只保存 source 映射、同步游标、版本和冲突状态。
6. 敏感 token 进入系统安全存储或桌面侧本地加密存储，不进入 workspace。
7. 导入后的内容会成为本地知识库的一部分，并参与本地 AI、搜索和 NoteApp 云同步。

## 架构

建议新增四层：

```text
Cloud Provider Adapter
  对接具体云端知识库 API，隐藏 provider 差异

Cloud Sync Engine
  管理全量导入、增量拉取、删除检测、冲突判断、游标推进

Workspace Materializer
  将云端文档转换并写入本地 workspace

Bridge API / UI
  为前端提供配置、同步触发、状态查看和冲突处理入口
```

建议代码落点：

```text
clients/desktop/cloud_kb/
  providers/
    base.py
    custom_http.py
    dingtalk.py
    notion.py
  sync_engine.py
  materializer.py
  state_store.py

apps/frontend/noteapp-web/scripts/sync-shell-bridge.mjs
  Add /api/cloud-sources/* local bridge endpoints

apps/frontend/noteapp-web/src/views/SettingsView.tsx
  Add Cloud KB settings section or tab
```

## Provider Adapter

每个 provider 适配到统一接口：

```python
class CloudKbProvider:
    def list_documents(self, cursor: str | None = None) -> CloudDocumentPage:
        ...

    def get_document(self, document_id: str) -> CloudDocument:
        ...

    def list_attachments(self, document_id: str) -> list[CloudAttachment]:
        ...

    def download_attachment(self, attachment_id: str) -> bytes:
        ...
```

统一文档模型：

```json
{
  "id": "cloud_doc_123",
  "title": "产品路线图",
  "path": ["部门知识库", "产品"],
  "url": "https://cloud.example.com/docs/cloud_doc_123",
  "version": "v42",
  "updated_at_ms": 1770000000000,
  "body_format": "markdown",
  "body": "# 产品路线图\n...",
  "attachments": []
}
```

如果云端提供 HTML、富文本 JSON 或 block model，provider adapter 负责先转换为中间模型，materializer 再输出 Markdown。

## 本地状态

每个 workspace 下保存 source 状态：

```text
.noteapp/cloud-sources/<source_id>.json
```

示例：

```json
{
  "schema_version": "v1",
  "source_id": "cloud-kb-main",
  "provider": "custom-http",
  "display_name": "公司云端知识库",
  "mode": "read_only",
  "last_sync_at_ms": 1770000000000,
  "cursor": "opaque-cloud-cursor",
  "documents": {
    "cloud_doc_123": {
      "file_id": "file_xxx",
      "path": "Cloud/部门知识库/产品/路线图.md",
      "cloud_version": "v42",
      "cloud_updated_at_ms": 1770000000000,
      "last_synced_content_hash": "sha256...",
      "last_local_content_hash": "sha256...",
      "status": "synced"
    }
  }
}
```

状态字段建议：

| Status | Meaning |
| --- | --- |
| `synced` | 本地文件与云端版本一致 |
| `local_modified` | 本地文件相对上次同步有改动 |
| `remote_modified` | 云端版本有更新，本地未改 |
| `conflict` | 本地和云端都已改动 |
| `remote_deleted` | 云端已删除，本地待确认处理 |
| `error` | 最近一次同步该文档失败 |

## Markdown Materialization

云端文档转换成本地 Markdown 时加入 frontmatter：

```markdown
---
source: cloud-kb
source_id: cloud-kb-main
cloud_doc_id: cloud_doc_123
cloud_url: https://cloud.example.com/docs/cloud_doc_123
cloud_version: v42
cloud_updated_at: 2026-05-20T10:00:00+08:00
sync_mode: read_only
---

# 产品路线图

正文...
```

路径映射：

```text
Cloud/<source display name>/<cloud path>/<title>.md
```

示例：

```text
Cloud/公司云端知识库/产品/路线图.md
Cloud/公司云端知识库/研发/API 规范.md
```

附件映射：

```text
Attachments/cloud-kb-main/cloud_doc_123/<filename>
```

Markdown 内使用相对路径：

```markdown
![image](../Attachments/cloud-kb-main/cloud_doc_123/image.png)
```

文件名冲突处理：

1. 同一个云端文档的本地 path 由 mapping 固定，不随标题轻易漂移。
2. 新文档生成路径时，如果目标已存在且不属于该 cloud document，自动加 `-2`、`-3` 后缀。
3. 如果云端标题重名，优先保持已有 path；重命名另行记录。

## 同步流程

### 初次导入

1. 用户在设置页添加 cloud source。
2. Bridge 调 desktop CLI 保存 source 配置。
3. Sync Engine 调 provider 拉取文档列表。
4. 对每个云端文档生成稳定本地 `file_id` 和 workspace path。
5. 下载正文和附件。
6. Materializer 写入 Markdown 和附件。
7. State Store 写入 `.noteapp/cloud-sources/<source_id>.json`。
8. 刷新 workspace files、搜索索引、双链索引和 sync shell snapshot。

### 增量同步

1. 读取 source state 中的 `cursor` 或 `last_sync_at_ms`。
2. Provider 拉取云端变更列表。
3. 对每个变更判断类型：新增、更新、删除、移动、重命名。
4. 检查本地文件当前 hash 与 `last_local_content_hash`。
5. 如果本地未改且云端更新，直接覆盖本地 Markdown。
6. 如果本地已改且云端也更新，进入冲突状态。
7. 如果云端删除，首版不直接删除本地文件，标记 `remote_deleted`。
8. 同步结束后更新 cursor、版本、hash 和索引。

### 删除处理

首版采用保守策略：

1. 云端删除不直接物理删除本地文件。
2. 在 state 中标记 `remote_deleted`。
3. 可选：在 frontmatter 中补充 `cloud_deleted: true`。
4. UI 提供“保留本地副本”或“移入回收站”。

## 冲突策略

冲突判断：

```text
local_current_hash != last_local_content_hash
and remote_version != cloud_version
=> conflict
```

首版策略：

1. 不覆盖用户本地文件。
2. 将云端新版本保存为旁路副本：

```text
Cloud Conflicts/<source display name>/<title>.cloud.md
```

3. 在 source state 中标记：

```json
{
  "status": "conflict",
  "conflict_reason": "local_and_remote_changed",
  "remote_conflict_path": "Cloud Conflicts/公司云端知识库/路线图.cloud.md"
}
```

4. UI 提供基础解决动作：
   - 保留本地
   - 采用云端
   - 另存副本
   - 手动合并

第一阶段只要求做到“检测冲突、不覆盖、生成云端副本、展示状态”。

## Bridge API

新增本地 bridge 端点：

```text
GET  /api/cloud-sources
POST /api/cloud-sources
GET  /api/cloud-sources/:id/status
POST /api/cloud-sources/:id/sync
POST /api/cloud-sources/:id/disconnect
GET  /api/cloud-sources/:id/conflicts
POST /api/cloud-sources/:id/conflicts/:conflictId/resolve
```

Bridge 调用 desktop CLI：

```text
pkb-desktop-sync cloud-source-list
pkb-desktop-sync cloud-source-add --input-json <path>
pkb-desktop-sync cloud-source-status --source-id <source_id>
pkb-desktop-sync cloud-source-sync --source-id <source_id>
pkb-desktop-sync cloud-source-conflicts --source-id <source_id>
pkb-desktop-sync cloud-source-resolve-conflict --input-json <path>
```

`POST /api/cloud-sources` 请求示例：

```json
{
  "provider": "custom-http",
  "display_name": "公司云端知识库",
  "base_url": "https://cloud.example.com/api",
  "auth_mode": "oauth",
  "mode": "read_only"
}
```

返回示例：

```json
{
  "ok": true,
  "source_id": "cloud-kb-main",
  "display_name": "公司云端知识库",
  "provider": "custom-http",
  "mode": "read_only"
}
```

## 前端 UI

建议在 Settings 中新增“云端知识库”区块：

1. Source 列表：名称、provider、模式、最近同步时间、文档数、冲突数。
2. 添加 source：provider、base URL、鉴权方式、导入路径前缀。
3. 立即同步按钮。
4. 同步进度和最近错误。
5. 冲突列表入口。

首版 UI 不需要复杂向导，控制在设置页内即可。

## 权限与安全

1. 云端 token 不写入 workspace，不写入 Markdown，不写入 `.noteapp/settings.json`。
2. 云端 token 优先使用系统安全存储；如果不可用，使用桌面侧本地加密文件并明确提示风险。
3. 导入后的 Markdown 和附件会参与本地搜索、AI 上下文、AI Wiki 编译。
4. 如果用户开启 NoteApp E2EE 同步，导入后的 Markdown 和附件会通过现有 E2EE 路径加密同步到 NoteApp 后端。
5. UI 必须提示：导入云端内容后，该内容会成为当前 workspace 的一部分。

## 测试策略

单元测试：

1. Provider response normalization。
2. Markdown materialization。
3. 文件名冲突和路径规范化。
4. Source state 读写和迁移。
5. hash 计算和冲突判断。

集成测试：

1. fake provider 全量导入。
2. fake provider 增量新增、更新、删除、重命名。
3. 本地修改 + 云端修改冲突。
4. 附件下载和 Markdown 相对路径转换。

回归验证：

1. 导入后 `/api/workspace/files` 可见。
2. 搜索能命中导入文档。
3. 图谱能读取导入文档 links。
4. AI Wiki 能基于导入文档编译。
5. 现有 sync shell snapshot 不被破坏。

## 阶段拆分

### M1: 只读全量导入

交付：

1. `custom-http` provider 最小实现。
2. source 配置保存。
3. 全量拉取文档和附件。
4. Markdown materialization。
5. workspace artifacts refresh。
6. 设置页显示 source 状态和“立即同步”。

验收：

1. 能从 fake/custom HTTP source 导入多篇文档。
2. 导入文档出现在 Explorer。
3. 搜索能命中导入内容。
4. 附件能打开或预览。
5. 云端 token 不出现在 workspace 文件中。

### M2: 增量同步

交付：

1. cursor/version state。
2. 新增、更新、删除、重命名处理。
3. 本地 hash 检测。
4. 同步 summary 和错误记录。

验收：

1. 云端新增文档后本地新增。
2. 云端更新文档后本地更新。
3. 云端删除文档后本地进入 `remote_deleted`。
4. 本地未改时可自动覆盖。
5. 本地已改时不覆盖。

### M3: 冲突 UI

交付：

1. 冲突列表。
2. 冲突详情。
3. 保留本地、采用云端、另存副本。

验收：

1. 本地和云端同时修改时生成冲突。
2. 用户选择保留本地后状态更新。
3. 用户选择采用云端后本地文件更新。
4. 所有解决动作刷新 workspace artifacts。

### M4: 双向写回，可选

交付：

1. 本地编辑发布回云端。
2. 云端 version precondition。
3. 写回失败保留本地内容。
4. 写回确认和审计记录。

验收：

1. 用户确认后可将本地修改发布到云端。
2. 云端版本变化时写回被拒绝并进入冲突。
3. 没有静默覆盖云端内容。

## 首版推荐范围

首版建议只做：

1. 一个 `custom-http` provider。
2. 只读全量导入。
3. 手动触发同步。
4. Markdown 和附件转换。
5. 基础 source state。
6. 冲突只检测，不自动合并。
7. 设置页展示 source 状态。

暂缓：

1. 双向写回。
2. OAuth 完整授权流。
3. 自动后台同步。
4. 复杂富文本双向转换。
5. 自动冲突合并。

## 主要风险

1. 云端文档模型与 Markdown 表达能力不一致，可能丢失布局或交互组件。
2. 云端权限模型可能比本地 workspace 更细，导入后权限边界会变宽。
3. 大规模知识库全量导入可能影响启动和索引性能。
4. 附件体积可能显著增加本地 workspace 和 NoteApp 同步成本。
5. 双向写回需要严格处理云端版本和审计，不适合首版直接做。

## 后续决策点

1. 首个 provider 是 `custom-http` 还是直接对接具体云端系统。
2. token 使用系统安全存储还是 provider 自带 OAuth token cache。
3. 云端删除是否默认进入 NoteApp trash。
4. 导入路径前缀是否允许用户自定义。
5. 是否需要 source-level include/exclude 规则。
