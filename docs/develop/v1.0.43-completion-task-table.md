## 并行推进建议

可以并行：

- M0 入口收口与 M1 移动笔记 API 设计可以并行。
- M1 附件产品化可与 M1 同步/冲突入口收口并行。
- M2 E2EE、断点续传、文件级版本历史、设备管理可以拆成四条线并行，但必须在 M2 回归套件处合流。
- M3 生产后端设计可以在 M2 协议设计稳定后提前启动。
- M4 AI 写回可以与 M3 后端生产化并行，前提是本地写回边界不依赖生产账号体系。

不建议并行：

- 不要在工作区模型未统一前继续扩展工作区相关 UI。
- 不要在真实 E2EE 设计未冻结前改造 blob 去重、文件版本保留和对象存储协议。
- 不要在同步页/冲突页入口策略未定前继续新增同步入口文案。

## 风险与缓冲

| 风险 | 影响 | 建议缓冲 |
| --- | --- | --- |
| E2EE、文件版本与对象存储协议耦合 | 改动面大，可能影响所有同步测试和版本保留策略 | M2 预留 1 周设计和联调缓冲 |
| 生产后端替换本地 `.data` | 数据模型迁移和并发 CAS 容易引入一致性 bug | M3 先做 shadow adapter，再切主路径 |
| 设备/tombstone 回收误删 | 数据安全高风险 | 回收前增加 dry-run 与审计日志 |
| AI 写回覆盖用户编辑 | 用户数据风险 | 默认 diff/确认，不自动覆盖 `user_edited` |
| 移动笔记影响双链/搜索/同步 | 多索引一致性风险 | 移动 API 必须集中刷新 filemap、search、links、sync snapshot |
| 文件版本历史导致云端存储增长 | 会议类文件会持续产生历史 blob | 增加 pin、数量/时间保留策略和可解释存储占用 |
