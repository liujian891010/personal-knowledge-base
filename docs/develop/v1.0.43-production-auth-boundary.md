# v1.0.43 Production Auth Boundary

Date: 2026-05-19

This note closes the production-account boundary for the current V1 backend and
records what is implemented versus what remains an explicit deployment policy.

## Implemented Server Boundary

| Area | Behavior |
| --- | --- |
| Password registration | `POST /auth/register` creates a password-backed account and stores only salted PBKDF2-SHA256 verifier material |
| Password login | `POST /auth/login` verifies password-backed accounts before creating a new device session |
| Dev/bootstrap registration | `POST /devices/register` remains available for local development and passwordless bootstrap accounts |
| Password-account protection | `POST /devices/register` rejects existing password-backed accounts with `password_required` |
| Access token | Opaque bearer token, one hour default lifetime |
| Refresh token | Opaque refresh token, 30 day default lifetime, rotated on refresh |
| Logout | Current session revoked; refresh token removed |
| Device revoke | Same-account device revoke only; sessions, refresh tokens, blob capabilities, and resumable upload sessions are invalidated |
| Vault API authorization | Every vault, commit, ack, file-version, device, tombstone, and blob-init route requires a valid bearer token |

## Password Flow

1. Client calls `POST /auth/register` with `account_key`, `password`,
   `device_name`, `platform`, and optional display/app/protocol metadata.
2. Server rejects passwords shorter than the configured minimum and rejects
   duplicate accounts.
3. Server stores PBKDF2-SHA256 verifier material and creates the first device
   session.
4. Client calls `POST /auth/login` with the same account key and password for
   later devices.
5. Wrong account key or password returns `invalid_credentials` without exposing
   which side failed.
6. Passwordless device registration cannot attach to a password-backed account.

## External IdP Strategy

External IdP is not enabled by default in v1.0.43. Production deployments that
need SSO should terminate OIDC/SAML at a trusted edge or future auth service and
map the verified subject to a stable account key before allowing sync-server
session creation.

Before enabling an IdP path, the deployment must define issuer, audience,
subject mapping, email verification rules, session TTL alignment, and account
deprovisioning behavior. The sync backend must continue to receive only verified
identity claims and must not accept unsigned client-provided identity headers.

## MFA Strategy

Built-in MFA challenges are not shipped in this backend slice. For public
multi-user production, MFA must be enforced by the external IdP or by a future
first-party MFA challenge endpoint before a session is issued.

Until that is implemented, the supported production posture is restricted
single-tenant or trusted-user deployment with strong passwords and short access
token lifetimes.

## Account Recovery Strategy

Self-service recovery is not enabled by default. Recovery must be an
operator-controlled process that verifies ownership outside the sync API, rotates
password verifier material, revokes existing sessions/devices as needed, and
never exposes vault encryption keys to the server.

The recovery package and vault key remain client-side concerns; server-side
account recovery can restore account access, but it cannot decrypt user content.

## Verification

Server tests cover:

1. Password registration stores verifier material and not plaintext passwords.
2. Password-backed accounts reject passwordless device registration.
3. Wrong passwords fail with `invalid_credentials`.
4. Correct passwords create authorized device sessions.
5. Duplicate registration is rejected.
6. Access token expiry, refresh rotation, logout, cross-account device revoke,
   and device capability revocation remain covered by backend tests.
