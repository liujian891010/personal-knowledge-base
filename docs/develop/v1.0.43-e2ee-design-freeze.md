# v1.0.43 E2EE 详细设计冻结

## 结论

`V1043-M2-01` 冻结为：同步 blob 使用真实客户端侧加密，服务端和对象存储只接触密文；`vault_key` 不上传、不托管、不通过服务端转发。V1 继续允许服务端持久化 manifest 元数据，包括 `content_hash`、`blob_id`、明文 `size` 和 `mtime`，因此 V1 安全边界是“云端不可解密内容明文”，不是“云端完全不可见内容指纹或文件规模”。

当前 `clients/desktop/crypto.py` 中的 placeholder provider 只保留为迁移前兼容和测试替身，不能作为生产默认实现。

## 密钥体系

- `vault_key`：每个 vault 创建时生成 32 字节随机密钥，是唯一数据根密钥。
- `content_key`：`HKDF-SHA256(ikm=vault_key, salt=utf8("noteapp:e2ee:v1:" + vault_id), info=utf8("blob-content"), length=32)`。
- `blob_id_key`：`HKDF-SHA256(ikm=vault_key, salt=utf8("noteapp:e2ee:v1:" + vault_id), info=utf8("blob-id"), length=32)`。
- `nonce_key`：`HKDF-SHA256(ikm=vault_key, salt=utf8("noteapp:e2ee:v1:" + vault_id), info=utf8("blob-nonce"), length=32)`。
- 禁止直接用 `vault_key` 做加密、HMAC 或 nonce 派生；新增用途必须新增独立 `info`。

## Blob 加密格式

- 明文哈希：`content_hash = "sha256:" + sha256(plaintext).hexdigest()`，继续写入 manifest。
- `blob_id = "blob-e2ee-v1-" + hmac_sha256(blob_id_key, utf8(content_hash)).hexdigest()`。
- `nonce = HKDF-SHA256(ikm=nonce_key, salt=None, info=utf8(content_hash), length=24)`。
- 加密算法：`XChaCha20-Poly1305`，密钥为 `content_key`，nonce 为上一步派生值。
- 密文落盘：`ciphertext || tag`，不写额外头；`encrypted_size = plaintext_size + 16`。
- AAD：V1 固定为空字节串，不使用 AAD。理由是当前 manifest 已绑定 `file_id/path/content_hash/blob_id` 并由 CAS 流程保护；V1.1 若要防御更强的跨文件密文替换，可引入 `aad = vault_id || blob_id` 并通过新 scheme 迁移。

解密时必须先按 manifest 的 `content_hash` 重建 nonce，解密后重新计算明文 `content_hash`；不一致必须视为错误密钥、损坏 blob 或服务端数据异常，不能写入工作区。

## 本地密钥存储与解锁

- 桌面端只允许把 `vault_key` 明文短暂驻留在进程内存中，退出、锁定或切换 vault 后清除。
- 持久化密钥材料必须进入系统安全存储：macOS Keychain、Windows DPAPI Credential Locker、Linux Secret Service 或等价实现。
- `.noteapp/` 里只允许保存非敏感加密状态，例如 `crypto_scheme=e2ee-v1`、`key_epoch=1`、创建时间和 provider 版本；不得保存明文 `vault_key` 或可直接解密的派生 key。
- 修改本地解锁口令只重新 wrap `vault_key`，不重加密历史 blob；旧 wrap 成功替换后必须删除。
- `key_epoch` V1 固定为 `1`。真正轮换 `vault_key` 不进 V1，后续需要多 key epoch 与全量迁移协议。

## 恢复包

恢复包是离线文件，恢复短语只是解开恢复包的材料，二者缺一不可。

恢复包 JSON 最小字段：

```json
{
  "schema_version": "e2ee-recovery-v1",
  "vault_id": "vault-001",
  "crypto_scheme": "e2ee-v1",
  "kdf": {
    "name": "argon2id",
    "memory_kib": 262144,
    "iterations": 3,
    "parallelism": 1,
    "salt_b64": "..."
  },
  "wrap": {
    "alg": "xchacha20-poly1305",
    "nonce_b64": "...",
    "ciphertext_b64": "..."
  },
  "created_at": 1770000000000,
  "checksum": "sha256:..."
}
```

- 恢复短语用于派生 `recovery_wrap_key`，只解密恢复包中的 `vault_key`。
- 恢复包必须包含 `vault_id`，新设备写入本地 `.vaultinfo` 时必须与云端 vault 一致。
- 仅输入恢复短语但没有恢复包时必须拒绝，并提示“请提供恢复包文件，或使用一台已解锁设备进行本地配对”。
- 若用户没有已解锁设备，同时丢失恢复包或恢复短语，数据不可恢复；产品文案不得承诺密码找回。

## 新设备接入

- 本地配对：已解锁设备通过局域网或扫码通道向新设备传输一次性加密接入包；服务端不参与 `vault_key` 中转。
- 离线恢复：用户登录账号后，导入恢复包并输入恢复短语；本地解开 `vault_key` 后再拉取云端 manifest 和密文 blob。
- 错误恢复短语、错误账号 vault、损坏恢复包都必须在解密或校验阶段失败，不能进入半初始化状态。

## 迁移策略

- 新建 vault：M2-02 起默认使用 `e2ee-v1`，不再生成 placeholder blob。
- 既有 placeholder vault：启动后识别 `crypto_scheme=placeholder-v1` 或缺失 scheme，进入一次性迁移流程。
- 迁移前必须先完成 pull，确保本地是最新 head；若存在冲突、缺失活跃文件或待恢复 journal，阻塞迁移。
- 迁移提交读取本地明文工作区，为所有 active 文件生成 `blob-e2ee-v1-*` 新 blob 并提交一次全量 manifest；`file_id/path/tombstone` 不变。
- 迁移成功后本地写入 `crypto_scheme=e2ee-v1`；旧 placeholder blob 只作为远端垃圾等待后续 GC，不在迁移中删除。
- 拉取端若遇到未知 `blob_id` scheme 或本地没有对应 `vault_key`，必须拒绝应用 manifest，不能回退到 placeholder 解密。

## 实现拆分

- `V1043-M2-02`：新增真实 `E2EEDesktopBlobCryptoProvider`，替换生产默认 provider；保留 placeholder 仅用于测试和显式兼容模式。
- `V1043-M2-03`：接入系统安全存储、本地锁定/解锁状态和错误密码提示。
- `V1043-M2-04`：实现恢复包导出、导入、本地配对和“只有恢复短语时拒绝”的产品流。
- `V1043-M2-16`：回归错误密钥、损坏 blob、迁移前后同步、恢复包缺失和多端拉取。

## 验收口径

- 服务端和对象存储收到的 blob payload 不包含明文片段。
- 同一 vault 内相同明文产生相同 `blob_id`；不同 vault 即使明文相同也产生不同 `blob_id`。
- 错误 `vault_key`、错误恢复短语或被篡改密文无法解密并明确报错。
- 新设备必须通过已解锁设备配对，或同时提供恢复包和恢复短语。
- 迁移后重命名、移动、删除和文件级版本历史仍按稳定 `file_id` 串联。
