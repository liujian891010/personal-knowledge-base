# 桌面客户端 + 中心同步服务开发任务拆解

## 1. 文档目的

本文件是在 [desktop-client-sync-service-plan.md](./desktop-client-sync-service-plan.md) 基础上的进一步下钻，目标不是再谈方向，而是直接拆到可开发、可排期、可验收的任务级别。

适用范围：

1. 桌面客户端产品化。
2. 本地服务层收口。
3. 中心同步服务生产化。
4. 第一版可交付能力的研发排期。

不在本文件展开的内容：

1. 纯 Web SaaS 化。
2. 移动端接入。
3. 多人实时协作。
4. 插件市场。

## 2. 当前代码基线

当前仓库可按以下结构理解：

1. `apps/frontend/noteapp-web`
   - 当前前端 UI 主体。
2. `apps/backend/noteapp-server`
   - 当前同步后端 MVP。
3. `clients`
   - 预留桌面客户端容器目录。
4. `packages`
   - 可复用基础能力沉淀目录。

当前真实问题不是“继续补几个页面”，而是“把开发态三进程体系收口为可交付产品形态”。

## 3. 开发总目标

第一版正式交付目标定义为：

1. 用户安装桌面客户端即可启动使用。
2. 用户可以登录、退出登录。
3. 用户可以选择、切换、修复本地工作区。
4. 用户可以完成 Markdown 编辑、文件树浏览、本地搜索、双链/反链、回收站、AI 文档。
5. 用户可以连接中心同步服务完成多设备同步。
6. 服务端具备基础账号、设备、vault、blob、revision 管理能力。

## 4. 研发分泳道

建议按 4 条泳道并行推进：

1. `Lane A / Desktop`
   - 桌面壳层、安装包、自动拉起本地服务。
2. `Lane B / Local Service`
   - bridge 收口、本地 API、工作区注册表、本地状态持久化。
3. `Lane C / Frontend`
   - UI 产品化、桌面态交互、错误提示、状态页。
4. `Lane D / Sync Server`
   - 账号、设备、vault 同步、blob、运维基础设施。

## 5. 里程碑

建议拆 4 个里程碑：

1. `M1` 桌面客户端内测可运行版
2. `M2` 中心同步服务 Beta 版
3. `M3` 联调与可交付版
4. `M4` 发布准备版

## 6. M1：桌面客户端内测可运行版

目标：把当前“手工启动三进程”改为“一个桌面应用可启动、可登录、可打开工作区、可编辑、可使用 AI 文档”。

### 6.1 Lane A / Desktop

#### DC-01 选型并固化桌面壳

交付物：

1. 桌面客户端技术选型结论。
2. 客户端目录结构。
3. 本地开发启动方式和打包方式说明。

建议实现：

1. 优先评估 Electron。
2. 如无硬性限制，不在本轮引入第二套前端渲染框架。

验收：

1. 仓库中存在独立桌面壳入口。
2. 桌面壳可加载现有前端页面。

依赖：

1. 无。

#### DC-02 桌面壳拉起本地服务进程

交付物：

1. 桌面壳启动时自动拉起本地服务进程。
2. 桌面壳退出时回收本地子进程。

验收：

1. 用户双击应用即可进入主界面。
2. 无需手工打开 terminal。
3. 异常退出后再次启动不会残留冲突端口。

依赖：

1. `LS-01`

#### DC-03 原生文件夹选择器接入

交付物：

1. 工作区选择改为桌面原生文件夹选择器。
2. 返回路径通过桌面壳传给本地服务层。

验收：

1. 不依赖浏览器能力选择文件夹。
2. 用户能稳定新增工作区。

依赖：

1. `LS-04`
2. `FE-03`

#### DC-04 Windows 安装包产物

交付物：

1. 可安装的 Windows 安装包。
2. 安装路径与用户数据目录策略。

验收：

1. 新机器可安装。
2. 启动后能够进入登录页。

依赖：

1. `DC-01`
2. `DC-02`

### 6.2 Lane B / Local Service

#### LS-01 收口本地服务入口

交付物：

1. 统一本地服务主入口。
2. 明确服务进程生命周期。
3. 清理开发态散落入口。

建议实现：

1. 把现有 `sync-shell-bridge.mjs` 演进为桌面本地服务入口。
2. 后续 workspace、draft、trash、AI chat、provider health 都从这一个服务暴露。

验收：

1. 本地服务通过单一入口启动。
2. 现有前端核心能力仍可使用。

依赖：

1. 无。

#### LS-02 统一错误码和错误响应结构

交付物：

1. 本地服务错误码约定。
2. 错误响应 JSON 结构。
3. 日志字段规范。

验收：

1. 前端能稳定识别“服务未启动 / 工作区失效 / 未登录 / 同步失败”等类型。
2. 所有本地 API 返回结构一致。

依赖：

1. `LS-01`

#### LS-03 本地健康检查接口

交付物：

1. `GET /health`
2. `GET /health/dependencies`

返回建议包括：

1. 本地服务状态
2. 工作区状态
3. 登录态摘要
4. 同步服务可达性
5. AI provider 配置有效性摘要

验收：

1. 前端可以直接消费健康状态。
2. 桌面壳可以在启动阶段轮询该接口。

依赖：

1. `LS-01`

#### LS-04 工作区注册表正式化

交付物：

1. 工作区 registry 存储结构。
2. 新增、删除、激活、重命名工作区接口。
3. 活动工作区切换后的缓存刷新策略。

验收：

1. 切换工作区不再出现旧数据残留。
2. 工作区失效时可提示修复。
3. 前端切换后只看到新工作区数据。

依赖：

1. `LS-01`

#### LS-05 本地用户态存储收口

交付物：

1. 登录信息持久化策略。
2. 工作区 registry 持久化策略。
3. AI 配置持久化策略。
4. AI 会话持久化策略。

建议实现：

1. 不再把正式登录态只放在 `sessionStorage`。
2. 由本地服务层统一落地并对前端提供读取接口。

验收：

1. 应用重启后用户信息仍可恢复。
2. 工作区与 AI 会话仍可恢复。

依赖：

1. `LS-01`

#### LS-06 本地 API 面收口

交付物：

1. 工作区文件 API
2. 内容 / 草稿 API
3. 搜索 API
4. 双链 API
5. 回收站 API
6. AI chat sessions API
7. AI provider health API

验收：

1. 前端核心页面不再依赖散乱入口或开发态 fallback。
2. 所有 API 路径、返回结构和错误码稳定。

依赖：

1. `LS-01`
2. `LS-02`
3. `LS-04`
4. `LS-05`

   - 完成内测回归

## 14. 结论

下一阶段不建议再把工作拆成零散功能点，而应按“交付链路”组织研发：

1. 先完成桌面客户端壳层和本地服务收口。
2. 再完成中心同步服务的账号、vault、revision、blob 正式化。
3. 最后完成联调、回归、安装包、更新和诊断能力。

只有这样，项目才会从“本地能跑”进入“别人可装、可用、可维护”的状态。
