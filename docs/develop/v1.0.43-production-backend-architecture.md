# v1.0.43 生产后端架构方案

生成日期：2026-05-18

对应任务：`V1043-M3-01`

## 结论

`V1043-M3-01` 冻结为：在保留现有同步协议主链路的前提下，把 `apps/backend/noteapp-server` 从本地开发 JSON store 演进为可部署中心同步服务。M3 不重写桌面端同步协议，不改变客户端 E2EE 边界，不让服务端持有明文内容或 `vault_key`。

生产后端采用三层持久化：

1. 关系型数据库：账号、设备、vault、revision、manifest、ack、capability、file_versions、tombstone GC、审计日志。
2. S3/OSS 兼容对象存储：只存加密 blob 和分片上传临时对象。
3. 后台任务：capability 过期清理、tombstone GC、对象存储孤儿对象清理、备份巡检。

数据库路线按阶段冻结：

| 阶段 | 数据库 | 适用范围 | 退出条件 |
| --- | --- | --- | --- |
| M3 内测 / V1 初期 | 托管 SQLite，优先 Turso / Cloudflare D1 这类带迁移和备份能力的服务 | < 1000 用户、单区域、低运维团队 | 写入延迟、事务语义、备份恢复或查询复杂度不满足生产目标 |
| V1 稳定期 | 继续托管 SQLite 或启动 PostgreSQL 迁移影子表 | 1000-5000 用户 | 出现跨区域、多租户统计、复杂审计或高并发写入需求 |
| V2+ | PostgreSQL，优先托管 PostgreSQL | > 5000 用户或团队/组织能力增强 | 无 |

实现必须通过 repository 层隔离数据库方言。`V1043-M3-03` 的 schema 和迁移脚本不得把业务逻辑绑定到本地 `.data/sync-state.json` 或单一云厂商 SDK。

## 当前基线

当前 `apps/backend/noteapp-server` 是 FastAPI 本地开发 MVP：

1. 状态默认写入 `apps/backend/noteapp-server/.data/sync-state.json`。
2. blob 默认写入 `.data/blobs/`。
3. CAS 只依赖单进程 `threading.RLock` 和 JSON 文件读写。
4. `POST /devices/register` 返回长期 bearer token，没有 refresh token 闭环。
5. 部分主链路仍允许本地 bootstrap 无 `Authorization` 请求。
6. capability 是本地 URL 替身，不是真实对象存储受控入口。

这些能力可以继续作为开发替身和迁移测试基线，但不能作为 M3 生产默认路径。

## 服务边界

生产后端保留一个部署单元，内部按模块分层：

1. `Auth / Account`：登录、refresh token、session、退出登录、账号级设备撤销。
2. `Device`：设备注册、心跳、last_seen、设备列表、设备注销。
3. `Vault`：vault、member、device membership、权限检查。
4. `Sync`：head、manifest、commit、resolve-intent、ack、tombstone GC。
5. `Blob`：blob check、upload-init、download-init、断点续传、对象存储适配。
6. `File Version`：commit 成功后写入 `file_versions`，支持列表、备注、pin 和保留策略。
7. `Ops`：健康检查、结构化日志、指标、审计、备份恢复。

M3 不拆微服务。除非部署和监控已证明单体无法承载，否则服务边界只体现在代码模块、repository 和接口层。

## 认证与授权

`V1043-M3-02` 必须先落账号和授权边界：

1. 所有 vault 级 API 必须要求 `Authorization: Bearer <access_token>`。
2. 移除本地 bootstrap 的无授权放宽逻辑；本地开发可通过显式 `NOTEAPP_AUTH_MODE=dev` 或测试 fixture 启用，不得在生产配置默认开启。
3. access token 短期有效，refresh token 长期有效且可轮换。
4. refresh token 按设备 / session 记录，退出登录或设备撤销必须立即失效。
5. 每个请求必须校验 user、device、vault membership，不能只按 `device_id` 判断。
6. 设备撤销后，该设备的 access token、refresh token、session、未使用 capability 都必须立即失效。
7. `401` 用于缺失或过期登录态，`403` 用于设备被撤销或无 vault 权限，不得混入 CAS 的 `409`。

新增账号接口可以在 M3 内部契约中定义，但不得破坏 `docs/contracts/sync-api.md` 已冻结的同步主链路。

## 数据模型冻结

生产数据库至少包含以下逻辑表。字段名可按 ORM / SQL 方言微调，但语义不得删减。

| 表 | 核心字段 | 说明 |
| --- | --- | --- |
| `users` | `id`, `login_key`, `display_name`, `status`, `created_at`, `updated_at` | 账号主体。M3 可先对接现有公司登录结果，不在服务端保存明文密码。 |
| `devices` | `id`, `user_id`, `name`, `platform`, `app_version`, `protocol_version`, `revoked_at`, `last_seen_at` | 账号级设备。 |
| `sessions` | `id`, `user_id`, `device_id`, `access_token_hash`, `refresh_token_hash`, `expires_at`, `revoked_at` | token 生命周期与注销。 |
| `vaults` | `id`, `owner_user_id`, `name`, `head_revision`, `created_at`, `updated_at` | 每个 vault 一条 head。 |
| `vault_members` | `vault_id`, `user_id`, `role`, `created_at`, `revoked_at` | V1 可只有 owner/member，后续扩展团队权限。 |
| `vault_device_state` | `vault_id`, `device_id`, `acked_revision`, `joined_at`, `last_seen_at`, `removed_at` | tombstone GC 的活跃设备集合来源。 |
| `revisions` | `vault_id`, `revision`, `base_revision`, `manifest_hash`, `created_by_device`, `created_at`, `commit_intent_id` | 单调 revision 记录。 |
| `manifests` | `vault_id`, `revision`, `payload_json`, `summary_hash`, `created_at` | 持久化 canonical manifest。 |
| `commit_intents` | `vault_id`, `commit_intent_id`, `intent_manifest_hash`, `revision`, `created_by_device`, `created_at` | 支持 resolve-intent 幂等恢复。 |
| `blobs` | `blob_id`, `vault_id`, `encrypted_size`, `encrypted_sha256`, `object_key`, `status`, `created_at` | 对象存储元数据，不保存明文。 |
| `blob_upload_sessions` | `id`, `vault_id`, `blob_id`, `device_id`, `expires_at`, `completed_at` | 断点续传上传恢复。 |
| `capabilities` | `id`, `vault_id`, `device_id`, `blob_id`, `kind`, `object_key`, `expires_at`, `revoked_at`, `used_at` | upload/download-init 生成的受控能力。 |
| `file_versions` | `version_id`, `vault_id`, `file_id`, `revision`, `blob_id`, `content_hash`, `path_at_revision`, `source`, `is_pinned`, `change_note`, `created_at` | `V1043-M2-08` 协议的生产持久化。 |
| `tombstone_gc_runs` | `id`, `vault_id`, `actor_device_id`, `eligible_revision`, `removed_count`, `created_at` | GC 审计与可解释提示。 |
| `audit_logs` | `id`, `user_id`, `device_id`, `vault_id`, `event_type`, `request_id`, `created_at`, `metadata_json` | 安全和排障。 |

约束：

1. `(vault_id, revision)` 必须唯一。
2. `(vault_id, commit_intent_id)` 必须唯一。
3. `file_versions` 必须按 `file_id` 查询稳定，不得按 path 串联版本。
4. `capabilities` 必须能按 `device_id` 批量撤销。
5. `vault_device_state` 中 `removed_at is null` 的设备才参与 tombstone GC 活跃设备集合。

## 对象存储

对象存储接入由 `V1043-M3-04` 实现：

1. 使用 S3/OSS 兼容 API，bucket 与 region 通过环境变量配置。
2. object key 由服务端生成，建议格式为 `vaults/{vault_id}/blobs/{sha256(blob_id)}`；客户端不得自行拼 key。
3. 客户端只通过 `upload-init` / `download-init` 获取一次性受控能力。
4. V1 不下发可长期脱离服务端鉴权的公开 URL。
5. 若使用云厂商短期直签 URL，服务端仍必须保存 capability 状态，并在设备撤销时拒绝后续服务端入口；如直签无法即时撤销，则生产默认应走服务端受控流式代理。
6. 上传完成前 blob 状态为 `pending`，只有加密大小和加密 sha256 校验通过后才变为 `available`。
7. 对象存储短时不可用时返回可解释错误，不得伪装成 CAS `409`。

## CAS 与并发控制

`V1043-M3-05` 的并发策略冻结为数据库事务优先：

1. commit 必须在单个事务中读取 vault head、校验 `base_revision`、写入 revision / manifest / file_versions / commit_intent、推进 head。
2. 对同一 `vault_id` 的 commit 必须串行化。托管 SQLite 阶段可通过事务写锁和条件更新实现；PostgreSQL 阶段使用 `SELECT ... FOR UPDATE` 或等价 advisory lock。
3. CAS 冲突只返回 `409`，响应仍按现有协议提供 `current_revision` / 当前 head 信息。
4. `resolve-intent` 必须按 `(vault_id, commit_intent_id, intent_manifest_hash)` 幂等查找，不能重新创建 revision。
5. commit 成功时可以同步推进提交设备的 `acked_revision`，但客户端 pull 后仍按 `/ack` 上报已应用 revision。
6. 文件版本记录与 revision 写入必须同事务提交；不得出现 revision 已成功但 `file_versions` 丢失的状态。

## Tombstone 与设备状态

生产 tombstone GC 继续沿用 M2 语义：

1. 新注册但未加入 vault 的设备不参与该 vault GC 判定。
2. 设备第一次 commit / ack / heartbeat 加入 vault 后，才进入该 vault 的活跃设备集合。
3. 被撤销或从 vault 移除的设备不再阻塞 GC。
4. tombstone 只有在所有活跃设备 `acked_revision >= deleted_revision` 且满足最小保留时间后才可回收。
5. GC 必须写入 `tombstone_gc_runs` 与 `audit_logs`，便于设备管理 UI 解释。

## 协议兼容性

同步主链路保持兼容：

1. 保留 `POST /devices/register`、`DELETE /devices/{deviceId}`、`GET /vaults/{vaultId}/head`、`GET /vaults/{vaultId}/manifests/{revision}`、`POST /vaults/{vaultId}/commits`、`POST /vaults/{vaultId}/commits/resolve-intent`、`POST /vaults/{vaultId}/ack`、`POST /vaults/{vaultId}/blobs/check`、`POST /vaults/{vaultId}/blobs/upload-init`、`POST /vaults/{vaultId}/blobs/download-init`。
2. M3 可以新增登录、刷新 token、退出登录、vault 创建 / 绑定接口。
3. `CreateCommitRequest.manifest` 仍是全量快照，不引入局部 patch。
4. manifest canonicalization、`summary_hash`、tombstone 回填、file_versions 语义保持与 M2 文档一致。
5. 生产后端不得要求客户端绕过 `download-init` 直接访问对象存储。

## 迁移路径

M3 迁移分四步执行：

1. `Repository` 抽象：从 `SyncStore` 提取账号、vault、revision、blob、capability、file_versions repository 接口，保留 JSON store 作为测试替身。
2. `Schema / Migration`：建立生产数据库 schema 和迁移命令，提供从 `.data/sync-state.json` 导入测试数据的 one-shot 工具。
3. `Shadow Adapter`：在测试环境中同一请求同时写 JSON store 与 DB repository，对比 head、manifest hash、ack、file_versions、capability 状态。
4. `Cutover`：生产配置默认启用 DB + 对象存储，JSON store 只允许测试和本地 dev profile。

迁移期间不得修改客户端本地 `filemap.json` 语义；服务端迁移只改变远端元数据和 blob 落点。

## 部署与运维

`V1043-M3-06` 至少交付：

1. 环境变量示例：数据库连接、对象存储 bucket、token 签名密钥、CORS、日志级别。
2. 健康检查：进程、数据库、对象存储、迁移版本。
3. 结构化日志：`request_id`、`user_id`、`device_id`、`vault_id`、错误码、耗时。
4. 指标：请求量、错误率、commit 冲突率、blob 上传失败率、capability 过期/撤销数、GC 删除数。
5. 备份：数据库每日备份，对象存储版本化或生命周期策略，恢复演练说明。
6. 回滚：应用版本回滚不能回滚已执行的 destructive migration；schema 变更必须 forward compatible。
