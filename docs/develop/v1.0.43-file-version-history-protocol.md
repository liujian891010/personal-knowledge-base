## 目标场景

用户本地工作区存在 `XXX.md`。每次会议后用户会修改该文件，并希望同步到云端后保留多个会议版本。后续用户需要：

- 查看 `XXX.md` 的历史会议版本列表。
- 给某个会议版本添加备注或标签。
- pin 关键版本，避免被保留策略回收。
- 预览旧版本、与当前版本 diff。
- 把旧版本恢复为当前版本，或另存为副本。

## 核心原则

- 版本链按稳定 `file_id` 串联，不按路径或文件名串联。
- `path_at_revision` 只记录该版本提交时的路径，文件移动或重命名后仍能查到同一条历史链。
- 历史版本引用已加密 blob，服务端不持有明文。
- 自动保存草稿不生成云端版本。只有成功 commit 后，或用户显式创建会议检查点后，才允许产生云端 `file_versions` 记录。
- 恢复旧版本不是回滚整个 vault，而是把旧版本内容写回当前文件，再产生新的 commit。

## 数据模型

`FileVersionRecord` 字段：

| 字段 | 含义 |
| --- | --- |
| `version_id` | 稳定版本 ID，基于 `vault_id/file_id/revision/blob_id/source` 生成 |
| `file_id` | 稳定文件 ID |
| `path_at_revision` | 该版本提交时的路径 |
| `revision` | 产生版本的 vault revision |
| `content_hash` | 明文内容 hash，用于解密后校验 |
| `blob_id` | 加密 blob ID |
| `size` | 明文大小 |
| `mtime` | 文件 mtime |
| `created_at` | commit 创建时间 |
| `created_by_device` | 产生版本的设备 |
| `source` | 版本来源 |
| `version_label` | 可选用户标签 |
| `change_note` | 可选版本备注 |
| `is_pinned` | 是否固定保留 |

`source` 允许值：

- `commit_success`：普通成功 commit 自动产生的版本记录。
- `manual_checkpoint`：用户显式创建普通版本检查点。
- `manual_meeting_checkpoint`：用户显式创建会议版本检查点，用于 `XXX.md` 这类会议文件。
- `restore`：从历史版本恢复后产生的新版本。

## 协议端点

新增 OpenAPI 契约：

- `POST /vaults/{vaultId}/file-versions/list`
- `PATCH /vaults/{vaultId}/file-versions/{versionId}`

`CreateCommitRequest` 新增可选字段：

- `file_version_directives`

该字段用于为本次 commit 的部分文件附加版本标签、备注、pin 和 source。自动保存流程不得提交该字段。

## 保留策略

协议冻结默认策略：

- `keep_latest = 50`
- `keep_pinned = true`
- `max_age_days = null`

后续 `M2-09` 落服务端时应按 file_id 维度执行保留策略。`is_pinned=true` 的版本不参与普通数量/时间回收。
