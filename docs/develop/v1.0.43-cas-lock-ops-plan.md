# v1.0.43 CAS Lock Operations Plan

Date: 2026-05-19

This plan closes the current PROD-05 boundary for commit CAS locking and
operational alerting.

## Production Strategy

The v1 production strategy is `sqlite-immediate`.

Production mode requires:

```text
NOTEAPP_SERVER_CAS_LOCK_STRATEGY=sqlite-immediate
```

The SQLite repository uses file-backed WAL connections and wraps mutable server
state writes in `BEGIN IMMEDIATE`. This means concurrent writers serialize on
the SQLite write lock before loading the current head revision. A stale commit
base is rejected as a CAS `409`, and the accepted commit keeps monotonic
revision advancement.

This strategy supports one production sync database with all writable server
processes sharing the same SQLite locking domain. It does not claim safe
active-active operation across independent database files or unreliable network
filesystem locks. That future topology should migrate to PostgreSQL
`SELECT ... FOR UPDATE`, advisory locks, or an equivalent provider transaction
lock around each vault head update.

## Required Monitoring Signals

`GET /metrics` exposes:

| Metric | Purpose |
| --- | --- |
| `commit_attempts_total` | Total commit requests that reached the commit route |
| `commit_conflicts_total` | CAS base or manifest conflicts returned to clients |
| `commit_conflict_rate` | Conflict ratio for commit attempts |
| `commit_cas_rejections_total` | CAS-layer rejections, including state-write conflicts |
| `state_write_conflicts_total` | Repository version conflicts while persisting state |
| `cas_lock_wait_events_total` | Number of SQLite write-lock acquisitions observed |
| `cas_lock_wait_total_ms` | Total observed write-lock wait time |
| `cas_lock_wait_max_ms` | Maximum observed write-lock wait time |
| `cas_lock_wait_average_ms` | Average observed write-lock wait time |
| `error_rate` | HTTP error ratio across all requests |

`GET /health/dependencies` exposes the active non-secret CAS policy under
`cas_lock`.

## Alert Threshold Configuration

Deployment configuration should set:

| Variable | Default | Alert meaning |
| --- | --- | --- |
| `NOTEAPP_SERVER_CAS_CONFLICT_RATE_ALERT_THRESHOLD` | `0.2` | Commit conflict rate is unexpectedly high |
| `NOTEAPP_SERVER_CAS_STATE_WRITE_CONFLICT_ALERT_THRESHOLD` | `1` | Repository state-write conflicts are present |
| `NOTEAPP_SERVER_CAS_LOCK_WAIT_MS_ALERT_THRESHOLD` | `250` | SQLite write-lock wait is elevated |
| `NOTEAPP_SERVER_CAS_ERROR_RATE_ALERT_THRESHOLD` | `0.05` | Request error rate is elevated |

Production alerting should evaluate the metric window used by the deployment
monitoring stack, not only the process lifetime values returned by the server.
The server exposes the counters and configured thresholds; the monitor owns
windowing, paging policy, and escalation routing.

## Incident Response

1. Check `commit_conflict_rate` first. A conflict spike with low error rate
   usually means concurrent clients need normal pull/retry handling.
2. Check `cas_lock_wait_max_ms` and `cas_lock_wait_average_ms`. Elevated wait
   means one writer is holding the SQLite transaction too long or the storage
   layer is slow.
3. Check `state_write_conflicts_total`. Non-zero values mean a stale repository
   version write escaped normal transaction serialization and should be treated
   as a correctness incident.
4. Check `error_rate` and structured request logs by `request_id`, `vault_id`,
   `device_id`, and `error_code`.
5. If lock wait remains elevated, reduce writer concurrency or route traffic to
   a single writer while preserving read traffic.

## Verification

Automated coverage:

1. Production mode rejects missing `NOTEAPP_SERVER_CAS_LOCK_STRATEGY`.
2. Health diagnostics expose the CAS lock strategy and alert thresholds.
3. Runtime metrics expose CAS rejections, state-write conflicts, and SQLite
   write-lock wait counters.
4. SQLite concurrent CAS tests verify exactly one accepted revision and one
   conflict for competing commits.
5. Production smoke asserts the SQLite profile, CAS policy diagnostics,
   concurrent CAS conflict behavior, CAS rejection metrics, and lock-wait
   metrics.
