# v1.0.43 Stability Regression

Task: `V1043-M5-06`

## Scope

This regression closes the two release-blocking stability gates:

1. A single file can sync continuously 1000 times without content corruption.
2. A long-offline old device does not resurrect a file deleted while it was offline.

## Script

Primary script:

```powershell
$env:PYTHONPATH='packages/vault-core/src;.'
python tests\e2e\desktop_sync_stability.py --iterations 1000
```

The script starts a temporary local sync server, uses the SQLite repository profile by default, creates temporary vault roots, and deletes all temporary data after completion.

Short development check:

```powershell
$env:PYTHONPATH='packages/vault-core/src;.'
python tests\e2e\desktop_sync_stability.py --iterations 5 --progress-every 1
```

CI wrapper:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\ci\v1043-acceptance.ps1 -Stability
```

## Scenario 1: 1000 Continuous Syncs

Flow:

1. Register two desktop devices in `vault-stability-continuous`.
2. Initialize both local vault roots.
3. For each iteration, write deterministic content with a SHA-256 marker to `Notes/stability.md` on device A.
4. Submit detected changes from device A.
5. Pull and apply on device B.
6. Assert device B's file content exactly matches device A's payload.
7. Assert final remote head revision equals the iteration count.
8. Assert both devices are clean after the final iteration.

Pass criteria:

1. Every iteration commits exactly once.
2. No pull returns stale content.
3. Final content hash matches the last iteration payload.
4. No local dirty changes remain.

## Scenario 2: Long-Offline Delete

Flow:

1. Register three desktop devices in `vault-stability-offline-delete`.
2. Device A creates `Notes/offline-delete.md` and commits revision 1.
3. Device B and device C pull revision 1.
4. Device C is treated as a clean old offline device for a simulated 30-day gap.
5. Device A deletes the note and commits revision 2.
6. Device B pulls revision 2 and confirms the canonical file is removed.
7. Before device C pulls, it attempts to submit detected changes; this must create no commit.
8. Device C pulls revision 2 and confirms the canonical file is removed.
9. Device C attempts another submit; this must create no commit and remote head must remain revision 2.

Pass criteria:

1. The stale clean offline device never creates a resurrection commit.
2. Remote head remains at the delete revision.
3. The canonical path is absent after reconnect.
4. Device C has no pending local changes after pull.
